# Визуализатор графа зависимостей пакетов

Конфигурационное управление, 3 семестр (осень 2026/2027), группа ИКБО-42-25.
Сборник практических работ № 2, **вариант 1**.

## 1. Общее описание

Консольное приложение (CLI) строит граф зависимостей пакета Ubuntu (apt)
и выводит его изображением в формате SVG. Информация о зависимостях
берётся напрямую из индекса пакетов репозитория (файл `Packages`), без
менеджеров пакетов и сторонних библиотек. Язык реализации — Python 3.9+,
внешние Python-библиотеки не нужны.

Ход работы по этапам (каждый этап — отдельный коммит):

| Этап | Содержание                                      |
|------|-------------------------------------------------|
| 1    | Минимальный прототип: параметры и их проверка   |
| 2    | Сбор данных: прямые зависимости из индекса apt  |
| 3    | Граф зависимостей (BFS с рекурсией), циклы, тестовый режим |
| 4    | Порядок загрузки зависимостей, сравнение с apt  |
| 5    | Визуализация: текст D2 и SVG, сравнение с apt-cache |

Структура проекта:

```
src/depgraph/   исходный код
tests/          модульные тесты (test_*.py)
tests/scripts/  bash-сценарии, которые запускают инструмент из ОС
examples/       тексты D2 для трёх реальных пакетов (nano, bash, curl)
tests/data/     локальный индекс Packages для тестов без сети
tests/repos/    тестовые репозитории (файлы с графами)
Makefile, run.sh   запуск и тесты
```

## 2. Описание всех функций и настроек

| Параметр              | Описание                                         | По умолчанию |
|-----------------------|--------------------------------------------------|--------------|
| `-p`, `--package`     | Имя анализируемого пакета                        | обязателен   |
| `-r`, `--repo`        | URL репозитория или путь к файлу тестового репозитория | обязателен |
| `-t`, `--test-mode`   | Режим тестового репозитория: `--repo` — путь к файлу | выключен |
| `-o`, `--output`      | Имя файла с изображением графа (`.svg`); рядом создаётся `.d2` | `graph.svg` |
| `--print-graph`       | Вывести граф текстом вместо изображения (этап 3) | выключен     |
| `--direct`            | Вывести только прямые зависимости (этап 2)       | выключен     |
| `--load-order`        | Вывести порядок загрузки зависимостей (этап 4)   | выключен     |
| `--print-params`      | Вывести все параметры в формате «ключ = значение» | выключен    |
| `-h`, `--help`        | Справка                                          |              |

Параметр `--print-params` — наследие этапа 1 (там параметры выводились
всегда). Пример вывода:

```
package   = bash
repo      = http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/
test_mode = false
output    = graph.svg
```

Проверки параметров (при ошибке: `error: ...` в stderr, код возврата 2):

- имя пакета: не пустое; в реальном режиме — по правилам Debian
  (строчные буквы, цифры, `+ - .`, от 2 символов); в тестовом режиме —
  только заглавные латинские буквы;
- `--repo`: в реальном режиме — URL со схемой `http`, `https` или `file`
  и с хостом; в тестовом режиме — существующий читаемый обычный файл;
- `--output`: не пустое, расширение `.svg`, не каталог, каталог для файла
  существует и доступен для записи;
- неизвестные параметры и параметры без значения.

### Репозиторий Ubuntu (этап 2)

В реальном режиме `--repo` — адрес каталога с индексом пакетов, например
`http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/`. Можно
указать и прямую ссылку на `Packages.gz`, `Packages.xz` или `Packages`;
для каталога пробуются именно в этом порядке. Допустимы схемы `http`,
`https` и `file` (последняя нужна для проверок без сети). Файл
скачивается стандартным `urllib`, распаковывается `gzip`/`lzma` и
разбирается собственным кодом (`src/depgraph/apt.py`).

Что считается прямой зависимостью:

- поля `Pre-Depends` и затем `Depends`; `Recommends`, `Suggests`,
  `Conflicts` и другие поля не учитываются;
- версии (`>= 1.2`), архитектуры (`:any`, `[amd64]`) отбрасываются;
- группа альтернатив `a | b`: выбирается первая альтернатива, которая
  есть в индексе; иначе первая виртуальная (её заменяет самый приоритетный
  пакет из поставщиков: `required`, `important`, `standard`, `optional`,
  `extra`, при равенстве — первый в индексе); иначе первая как есть (пакета нет в этом индексе, в
  отчёте стоит пометка `not in this index`);
- повторные зависимости на один и тот же пакет объединяются;
- если в индексе несколько записей с одним именем, берётся первая.

Индекс одного компонента (`main`) не содержит пакетов из `universe`:
такие зависимости помечаются как отсутствующие в индексе.

Ошибки (`error: ...`, код 1): нет сети или хоста, индекс не найден,
повреждённый архив, пустой индекс, пакета нет в репозитории.

### Граф зависимостей (этап 3)

Граф всех транзитивных зависимостей пакета строится всегда. С параметром
`--print-graph` (на этапе 3 это было поведением по умолчанию) он
выводится списком смежности (пакеты — в порядке обхода в ширину), затем
сообщаются найденные циклы:

```
Dependency graph of A: 6 packages, 8 edges
  A: B, C
  B: D
  ...
Cyclic dependencies found (1):
  B -> D -> F -> B
```

Алгоритм (`src/depgraph/graph.py`): обход в ширину, записанный через
рекурсию по уровням. Функция `_bfs_level` получает список пакетов
текущего уровня, записывает их зависимости в граф и вызывает сама себя
для следующего уровня. В следующий уровень попадают только пакеты,
которых ещё нет в графе, поэтому каждый пакет обрабатывается один раз,
а циклические зависимости не зацикливают обход. Слишком глубокая цепочка
(переполнение рекурсии) даёт понятную ошибку, а не трассировку.

Циклы ищет отдельная функция `find_cycles` (обход в глубину без
рекурсии): каждое ребро на пакет, лежащий на текущем пути, выводится
как цикл `A -> B -> C -> A`. Циклы в реальных данных встречаются:
например, `libc6 -> libgcc-s1 -> libc6`.

### Тестовый режим (этап 3)

С `--test-mode` параметр `--repo` — путь к файлу с описанием графа.
Пакеты называются заглавными латинскими буквами:

```
# комментарий
A: B C        # A зависит от B и C
B: C
C:            # у C зависимостей нет
```

Правила: одна строка на пакет; зависимости через пробел или запятую;
повторы убираются; пакет, упомянутый только как зависимость, считается
пакетом без зависимостей; недостижимые от анализируемого пакета вершины в
граф не входят. Ошибки файла (нет двоеточия, недопустимое имя, пакет
описан дважды, пустой файл) выводятся с номером строки, код возврата 1.
Готовые примеры лежат в `tests/repos/`.

### Порядок загрузки (этап 4)

`--load-order` выводит пакеты в порядке, в котором их нужно загружать:
сначала то, что нужно другим, анализируемый пакет — последний.

```
Load order for nano: 6 packages, dependencies first
  1. gcc-14-base
  2. libgcc-s1
  3. libc6
  4. libtinfo6
  5. libncursesw6
  6. nano
Order inside cycles is arbitrary (1 found):
  libc6 -> libgcc-s1 -> libc6
```

Алгоритм (`src/depgraph/order.py`): обход графа в глубину без рекурсии,
пакет записывается в результат после всех своих зависимостей
(post-order). Зависимости посещаются в порядке индекса. Ребро на уже
посещённый пакет пропускается, поэтому циклы «разрываются»: порядок
внутри цикла определяется порядком обхода, и об этом выводится
предупреждение со списком циклов.

#### Сравнение с apt

Скрипт `tests/scripts/compare_apt.sh ПАКЕТ [СЬЮТ]` запускает `apt-get -s
install --no-install-recommends` (только имитация) с изолированной
настройкой: один репозиторий `noble main` (тот же индекс, что читает
инструмент) и пустой список установленных пакетов. Сравниваются множество
пакетов и порядок строк `Inst` (порядок распаковки). Результат для
Ubuntu 24.04 (noble, main):

| Пакет          | Пакетов в apt | В инструменте | Множества | Порядок |
|----------------|--------------:|--------------:|-----------|---------|
| nano           | 6             | 6             | совпали   | совпал  |
| bash           | 9             | 9             | совпали   | отличается |
| dash           | 15            | 15            | совпали   | отличается |
| coreutils      | 10            | 10            | совпали   | отличается |
| perl-base      | 15            | 15            | совпали   | отличается |
| vim-tiny       | 9             | 9             | совпали   | отличается |
| python3-minimal | 18           | 18            | совпали   | отличается |
| curl           | 32            | 32            | совпали   | отличается |
| openssh-client | 42            | 42            | совпали   | отличается |

Пример расхождения порядка (`bash`):

```
apt (Inst)      инструмент
gcc-14-base     gcc-14-base
libc6           libgcc-s1
libgcc-s1       libc6
mawk            libtinfo6
libcrypt1       mawk
base-files      libcrypt1
libtinfo6       base-files
debianutils     debianutils
bash            bash
```

Почему порядок отличается, хотя множества совпадают:

1. Топологический порядок неоднозначен. Любая перестановка, где каждая
   зависимость стоит раньше зависимого, корректна. Проверка показала:
   в порядке инструмента и в порядке `apt` нет ни одного нарушения
   «зависимость раньше зависимого» (кроме рёбер внутри циклов).
2. `apt` упорядочивает пакеты своим алгоритмом (учитывает Pre-Depends,
   приоритеты, разделяет распаковку `Inst` и настройку `Conf`), а
   инструмент просто идёт по зависимостям в порядке записи. Например, у
   `bash` в Pre-Depends записаны `libc6, libtinfo6`, поэтому инструмент
   ставит `libtinfo6` сразу после `libc6`, а `apt` откладывает его. Для
   `dash` и `coreutils` порядок инструмента совпал с порядком настройки
   (`Conf`) у `apt`.
3. Цикл `libc6 <-> libgcc-s1` в любом случае нужно «разорвать»: `apt`
   распаковывает `libc6` первым, инструмент — `libgcc-s1`.
4. Что могло бы давать расхождения в составе пакетов, но здесь не
   проявилось: `apt` по умолчанию ставит Recommends (в сравнении
   отключено), не ставит уже установленные пакеты (используется пустой
   список установленных), выбирает версии из нескольких репозиториев
   (используется один). Выбор поставщика виртуального пакета
   (например, `awk` -> `mawk`) инструмент повторяет по приоритету.

### Визуализация (этап 5)

Без дополнительных параметров инструмент строит граф и сохраняет:

1. текстовое представление на языке диаграмм [D2](https://d2lang.com) —
   файл с тем же именем, что у изображения, но с расширением `.d2`
   (`graph.svg` -> `graph.d2`; `src/depgraph/d2.py`);
2. SVG-изображение — его строит программа `d2` из этого текста
   (`src/depgraph/render.py`).

Правила диаграммы: стрелка `A -> B` означает «пакет A зависит от B»;
анализируемый пакет закрашен жёлтым; рёбра, входящие в циклы, красные
(в том числе петля пакета на самого себя). Имена пакетов записываются в
кавычках, потому что точка в D2 означает вложенность, а имена вроде
`python3.12` и `libstdc++6` содержат точки и плюсы.

Программа `d2` — единственный внешний инструмент, только для рисования
(зависимости она не получает). Установка: <https://d2lang.com/tour/install>
(Linux/macOS: `curl -fsSL https://d2lang.com/install.sh | sh -s --`).
Если `d2` нет, `.d2`-файл всё равно сохраняется, а программа сообщает
об ошибке (код 1). Другое имя или путь к программе можно задать
переменной окружения `DEPGRAPH_D2`.

Три примера для реальных пакетов Ubuntu 24.04 (noble, main) лежат в
`examples/*.d2`; изображение получается командой
`d2 examples/nano.d2 nano.svg` или самим инструментом:

| Пакет | Пакетов | Рёбер | Рёбер в циклах | Цикл                    |
|-------|--------:|------:|---------------:|-------------------------|
| nano  | 6       | 9     | 2              | libc6 <-> libgcc-s1     |
| bash  | 9       | 14    | 2              | libc6 <-> libgcc-s1     |
| curl  | 32      | 81    | 2              | libc6 <-> libgcc-s1     |

```
./run.sh -p nano -r http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/ -o nano.svg
./run.sh -p bash -r http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/ -o bash.svg
./run.sh -p curl -r http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/ -o curl.svg
```

SVG-файлы в репозиторий не добавляются (`.gitignore`): D2 встраивает в
них шрифты длинными строками.

#### Сравнение со штатными средствами apt

Скрипт `tests/scripts/compare_apt_graph.sh ПАКЕТ [СЬЮТ]` сравнивает граф
с `apt-cache dotty` (рисунок Graphviz) и `apt-cache depends --recurse` на
том же индексе `noble main` (изолированная настройка apt, как в
`compare_apt.sh`). Связи Suggests в `dotty` (зелёные) не учитываются,
потому что инструмент их не рисует.

| Пакет | Рёбер dotty (без Suggests) | Рёбер инструмента | `depends --recurse`, пакетов | Пакетов инструмента |
|-------|---------------------------:|------------------:|-----------------------------:|--------------------:|
| nano  | 9                          | 9                 | 6                            | 6                   |
| bash  | 13                         | 14                | 15                           | 9                   |
| curl  | 81                         | 81                | 32                           | 32                  |

У `nano` графы совпадают полностью. Причины расхождений:

1. **Виртуальные пакеты.** `dotty` рисует виртуальный пакет отдельной
   вершиной (`awk`, `libssl3`, `libnettle8`) и дальше не раскрывает.
   Инструмент заменяет его настоящим поставщиком: `awk` -> `mawk`,
   `libssl3` -> `libssl3t64`. Поэтому у `bash` рёбра
   `base-files -> awk` (dotty) и `base-files -> mawk`, `mawk -> libc6`
   (инструмент), а у `curl` четыре ребра различаются только именем
   (`libssl3` и `libssl3t64`, `libnettle8` и `libnettle8t64` и т.д.).
2. **Альтернативы.** `apt-cache depends --recurse` раскрывает все
   варианты виртуального пакета: для `awk` — и `gawk`, и `mawk` со всеми
   их зависимостями (15 пакетов у `bash`). Инструмент, как и `apt` при
   установке, выбирает один вариант (самый приоритетный, `mawk`), и в
   графе 9 пакетов, как в списке установки `apt-get -s install`.
3. **Suggests.** `dotty` добавляет зелёные рёбра Suggests (21, 27 и 54
   ребра у nano, bash и curl), которых нет в Depends; инструмент учитывает
   только Pre-Depends и Depends.
4. **Оформление.** `dotty` не выделяет циклы (`libc6 <-> libgcc-s1`
   нарисован обычными рёбрами) и склеивает рёбра (`concentrate=true`);
   инструмент красит рёбра циклов и выделяет анализируемый пакет. Рисует
   Graphviz у `dotty` и D2 у инструмента, поэтому раскладка отличается.

## 3. Сборка и запуск тестов

Сборка не нужна. Требуется Python 3.9+; для SVG — программа `d2`.

```
./run.sh -p bash -r http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/
make test          # модульные тесты и bash-сценарии
make test-unit     # только модульные тесты
make lint          # flake8 (нужен pip install flake8)
```

Модульные тесты не требуют сети. Сценарии `tests/scripts/stage*.sh`
дополнительно обращаются к archive.ubuntu.com, если он доступен.
